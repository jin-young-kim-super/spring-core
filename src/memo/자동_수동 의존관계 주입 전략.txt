@Autowired는 우선적으로 타입으로 빈을 조회하기에 똑같은 타입의 빈이 등록이 되어 있으면 그 타입의 자식 객체 모두를 빈으로 등록하기에 
2개 이상의 의존 관계 대상 빈이 있을 수가 있다. 
이때 @Qualifier과 @Primary를 사용해서 특정 빈을 의존 관계 주입할 수도 있다. 자동 주입 vs 수동 주입 

업무 로직 : 자동 주입
기술 로직 : 수동 주입
→위 전략을 택하자

물론 설정 정보(@Configuration 기반의 Appconfig 클래스)를 기반으로 애플리케이션을 구성하는 부분(구성 영역)과 실제 동작하는 부분(주로 비지니즈 로직 등의
사용 영역)을 명확히 나누는 것이 【이상적】이다. 왜냐하면 애플리케이션의 구성 객체들을 한 눈에 파악할 수 있기 때문이다. 
그러나 현실에서는 개발자가 스프링 빈을 등록할 때마다 @Component 스캔만 넣어주면 끝나는 일을
@Confiugration 설정 정보에 들어가서 일일이 @Bean을 적고 거기 밑에다가 메서드를 만들고 또 그 내부에서 의존 관계 주입 대상 구현체를 new 해서 만들어
주는 것이 매우 번거로운 것이 현실이다. 또 만약 관리할 빈이 많아서 설정 정보가 비대해지면 설정 정보를 관리하는 것 자체가 부담이 된다. 

그래서 실무에서는 아래와 같은 기준으로 빈을 자동 등록하고 수동 등록을 한다. 

업로 로직 빈 : 자동 주입
→  업무 로직 빈은 @Configuration 기반의 AppConfig 클래스의 수동 설정을 안 해서 애플리케이션의 구성 빈을 한 눈에 파악 못하는 단점이 확실히 존재한다. 
그러나 자동 주입을 해도 괜찮은 것이 업무 로직 빈이 많더라도 업무 로직은 【컨트롤러->서비스->레포지토리】라는 유사한 패턴으로 개발이 된다. 
그러므로 만약 문제가 발생을 하더라도 어디에서 문제가 생겼는 지 바로 추측이 가능하다. 고로 업무 로직 빈의 경우 자동 주입 패턴을 쓰는 것이 실무에서는 현실적이다. 

기술 로직 빈 : 수동 주입
→ 데이터베이스 연결이나 공통 로그 처리 등의 AOP 로직! 즉 업무 로직을 지원하기위한 하부 기술 및 공통 기술들이다. 
이와 같은 빈들은 업무 로직 빈에 비해서 숫자가 굉장히 적다. 업로 로직의 경우 문제 발생 시 어디가 문제인지 파악하기 쉬운 반면 
기술 로직은 문제 발생 시 어디가 문제인지 명확하게 잘 들어나지 않고 특정 기술 로직 빈이 잘 등록되서 적용되고 있는 지 조차 모르고 지나칠 떄가 많다. 그로 인해 이런 기술 지원 로직 빈인 하나의 파일 안에 수동 설정을 해서 모아 두는 것이 한 눈에 어떤 기술 지원 로직 빈이 주입 되었고 
어느 기술 지원 빈에 문제가 생겼는 지 빠르게 파악이 가능하다. 

예외 : 위와 같이 전략 패턴 등에 의해서 Map, List의 빈의 경우는 수동 설정하는 것이 좋다. 

예를 들어 아래의 경우 DiscountPolicy에 여러 빈들이 등록되어 있는 경우, 내가 개발했을 때는 어떤 빈들이 주입됐는 지 알지만 다른 개발자들이 이걸
봤을 때 코드를 일일이 뒤져봐야 한다( DiscountPolicy가 하나만 있는 경우에는 그냥 인터페이스에 있는 메서드만 잘 사용하면 되겠지라는 생각이 들지만 
2개 이상인 경우 어떤 할인 정책들이 있는지 알고서 개발을 해야 하기에 뒤져 봐야 한다)
ex) private final Map<String, DiscountPolicy> policyMap;

그렇기 때문에 아래와 같이 수동 설정을 통해 어떤 할인 정책들이 적용되어 있는지 한 눈에 파악하기 쉽게 하는 것이 좋다. 
@Configuration
class AppConfig {
@Bean
public DiscountPolicy fixDiscountPolicy() {
	return new fixDiscountPolicy();
}

@Bean
public DiscountPolicy rateDiscountPolicy() {
	return new rateDiscountPolicy();
}
}
※그럼에도 자동 등록을 하고 싶을 때에는 하나의 패키지에 DiscountPolicy의 구현체들만 따로 등록해 두어서 
개발자들이 파악하기 쉽게 하는 것이 좋다.
