스프링 빈의 이벤트 라이프사이클 : 스프링 컨테이너 생성 → 스프링 빈 생성 →　의존관계 주입 →　초기화 콜백(초기화 작업) →　사용　→　 소멸전 콜백 →　스프링 종료
※예외적으로 생성자 의존 관계 주입은 스프링 빈 생성과 의존 관계 주입이 한 번에 일어난다(수정자 의존 관계 주입/필드 의존 관계 주입에서는 위 라이프 사이클을 지킨다)
※스프링이 말하는 초기화 콜백의 “초기화”는 의존관계 주입(DI) 이후에 수행되는 추가적인 준비 작업
정리
・의존 관계 주입(DI) = 객체에게 필요한 의존성을 넣는다.
・초기화 작업 = 스프링에서 초기화 작업이란 DI와 구분해서, 의존관계 주입이 끝난 뒤 실제로 객체를 사용할 수 있게 수행하는 별도의 준비 작업을 의미

Q. 스프링에서 빈 라이프 사이클을 만든 이유는?
A. 객체의 생성 작업, 의존관계 주입 작업과 [외부 자원 초기화/해제] 작업을 분리하여 안전하게 사용/해제하기 위함이다.
지금 NetworkClinet 빈을 보자!!!
생성자 안에 초기화 작업(connect)를 하고 있다. 근데 의존 관계 주입에 해당하는 setUrl()은 빈 객체가 생성되고 초기화 작업이 시작되고 난 이후에
호출이 된다. 그 결과 초기화 작업 실행 시점에는 아직 url에 세팅돼 있지 않아서 NetworkClinet를 사용하지 못하고 있다.
이러한 점 때문에 빈 객체 생성 -> 의존 관계 주입이 완료된 후 초기화 작업 실행을 보장함으로써 빈의 안전한 사용과 해제를 스프링은 보장을 한다.
즉,지금 작성한 NetworkClinet 코드는 왜 스프링 빈 라이프 사이클이 필요한지를 보여주기 위한 잘못된 코드 예시이다.
※ 대부분의 초기화 작업은 빈 생성/의존 관계 주입이 끝나야지만 진행 가능한 작업이 대부분이다.


스프링 빈 라이프 사이클 - 초기화 작업

・스프링 빈 생성과 초기화 작업은 분리하는 것이 좋다. 
→ 예를 들어 DataSource 객체를 생성한다고 하자. 
그리고 초기화 작업은 스프링 빈 생성이 되고 의존 관계 주입이 끝나서, 이렇게 생성된 값들을 활용하여 외부 DB 서버와 커넥션 풀 생성하고 연결하는 【무거운】 작업이다. 
언뜻 보기에는 그냥 객체 생성 시에 초기화 작업이 바로 일어나도록 생성자 안에 초기화 코드를 삽입하는 것이 좋아 보인다. 
그러나 유지/보수 관점에서 위와 같이 【무거운】 초기화 작업의 경우에는 객체 생성과 초기화 작업을 명확히 분리하는 것이 좋다. 
그리고 대부분의 초기화 작업은 의존 관계를 활용한 작업이 대부분이기에 그러한 점에서도 객체 생성과 초기화 작업을 분리하는 것이 좋은 설계이다. 


※초기화 작업이 만약 단순한 객체 내 필드값 세팅 등의 가벼운 작업일 경우에는 생성자 내에서 초기화 코드를 삽입하여도 ㄱㅊ
→ 그러나 코드의 일관성을 위하여 초기화 작업은 되도록 일관되게 분리하는 것이 나는 개인적으로 좋다고 생각한다. 
왜냐하면 추후 그 초기화 작업에 의존 관계를 사용하도록 요구 사항이 변경될 때를 생각을 하면 분리하는 것이 유지 보수가 쉽기 때문이다. 
나는 이게 객체 생성과 초기화 작업을 분리하는 핵심 이유인 것 같다.



스프링의 초기화 콜백, 종료전 콜백 3가지 지원 방법
  ・InitializingBean(afterPropertiesSet 메서드로 초기화 콜백 지원), DisposableBean(destroy 메서드로 종료전 콜백 지원)
  → 위 인터페이스는 스프링이 제공하는 스프링 프레임워크에서만 동작하는 초기화 콜백, 종료전 콜백을 지원하는 것이다.
  근데 위 인터페이스를 사용하여 초기화 작업 등을 안 하는 것이 좋다.
  왜냐하면 3가지 이유가 있다.

     ・스프링 프레임 워크에 의존적
     → 위 인터페이스는 스프링 프레임워크의 빈 라이플 사이클 중 실행되는 인터페이스이므로 만약 위 인터페이스를 상속받은 객체의 경우
     스프링 프레임 워크 없이는 순수 자바 코드로 테스트 코드를 만드는 것이 불가능하다.
     또한 객체 내에 스프링 전용 인터페이스가 있기 때문에 다른 객체 내에서 스프링 프레임워크 없이는 해당 객체를 재사용하는 것이 어렵다.
     ( 좋은 객체 설계란, 그 객체의 비지니즈 로직이 프레임워크에 의존하지 않도록 만드는 것이다. 그래야 순수 자바 코드로 테스트 코드를 만들 수 있다)

     ・메서드명 변경 불가능
     → afterPropertiesSet,  destroy 메서드의 경우 우선 의미 전달이 힘들다. 그리고 무엇보다도 이 메서드들은 객체 내에서 딱 1번만 사용이 가능하다.
     경우에 따라서는 여러 초기화 작업이 있을 수 있기 때문에 이런 경우에 치명적이다.

     ・개발자가 코드를 고칠 수 없는 외부 라이브러리에 적용 불가(클래스 파일로 적용되는 외부 라이브러리는 변경이 불가능)
     → 만약 우리가 외부 라이브러리를 다운로드 하여 그 객체를 빈 등록을 했다고 하자. 근데  초기화 작업, 종료전 콜백 작업을 위해
     InitializingBean, DisposableBean인터페이스를 상속시키도록 코드를 변경하지 못한다.
     ※ 위와 같은 이유로 현재는 거의 사용 안됨
