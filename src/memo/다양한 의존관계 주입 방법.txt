・수동 빈 vs 자동 빈
수동 빈 : @Configuration + @Bean + 자바 클래스 코드
자동 빈 : @ComoponentScan +@Component + 자바 클래스 코드
→스프링 부트는 위와 같은 애노테이션과 자바 클래스 코드를 개발자 대신 자동으로 만들어 줄 뿐이다. 

・순수 스프링 프레임워크만으로 만약 A라는 빈이름으로 수동/자동 설정 클래스에서 중복으로 빈을 등록하려고 하면, 수동 설정이 우선권을 가지기 때문에 
수동의 빈이 등록이 된다. 
→ 그러나 실무에서 개발자가 의도적으로 수동/자동에서 똑같은 빈 이름을 등록하려고 했을 때 설정 정보가 꼬여 오류를 일이키기 십상이다. 
그래서 【스프링 부트】에서는 이러한 것을 방지하기 위해서 스프링 부트로 자동 빈 등록 시, 수동/자동에서 똑같은 빈 이름이 등록되면 그냥 에러를 내버리는 전략을 채택하였다. 
※다만 기억해야 할 것은 순수 스프링 프레임워크에서는 여전히 우선권 전략을 택한다. 그리고 스프링 부트도 application.property 파일에서 설정을 하면 부트에서도 우선권 전략으로 
변경이 가능하다.다만 스프링 부트의 기본 전략을 따르는 것이 협업에 좋다 


・개발은 혼자하는 것이 아니라 협업이기에 조금이라도 애매한 짓은 안 하는 게 좋다. 
→ 개발을 하다보면 이런 경우가 있다. 
추상화 등을 통해서 코드양을 줄일 수가 있고 코드가 더 깔끔하다. 반대로 코드양은 조금 늘지만 이게 누가 보기에도 명확하게 파악이 되고 기능적으로도 안정적이라면
대부분의 경우 후자를 선택하는 것이 낫다. 
실무 개발에 있어서는 협업 중심이기에 다른 팀원에게 조금이라도 애매한 느낌을 주는 코드를 만들어서는 안된다. 
그럴바에는 코드양이 조금 늘더라도 에러 발생율이 조금이라도 적은 방식을 택하는 것이 나중에 에러 대응 시간 측면에서 비용이 더 적게 든다. 
  

・모든 변경에 열려 있는 코드는 좋은 아키텍처가 아니다
→ 예를 들어 의존 관계 객체는 애플리케이션 시작부터 종료까지 변하지 않는다.
그런데 만약 초기 설계자가 생성자 방식의 의존 관계 자동 주입를 통해서 호출 시점에 의존 관계 객체를 불변하게 만들어 놓았다고 치자. 
근데 여기서 추가적으로 setter 코드를 만들어 놓게 되면 후속 개발자가 setter를 사용해서 잘못된 의존관계 객체를 주입시킬 수가 있어서 치명적인 에러를 일으키게 될 가능성이 있다. 
이 사례에서도 보면 알듯이 허용되는 변경 범위 밖의 변경을 허용하는 아키텍처는 절대 만들면 안된다. 
좋은 아키텍처는 항상 허용되는 변경 범의 밖의 변경을 허용하지 않는 불변의 아키텍처이다. 
※이러한 이유에서 아무 생각 없이 setter 남발은 절대 금지!!!! 
※위의 맥락에서 스프링의 의존 관계는 왠만해서는 생성자를 통한 의존 관계 자동 주입을 사용하는 것이 좋다. 
테스트 코드에서 의존 관계를 변경하는 등의 필요에 의해서 setter에 의한 의존 관계 자동 주입을 혼합 사용하는 것이 좋다(사실 DIP를 잘 준수한 코드이면 생성자 방식으로도 얼마든지 
유연한 테스트 코드를 만들 수 있기에 신중하게 사용하자!!)

 
・생성자 의존 관계 자동 주입 vs setter 의존 관계 자동 주입
생성자 의존 관계 자동 주입
　・의존 관계 객체가 【불변/필수】일 때 사용(단 setter를 통해서 의존 관계 객체 변경이 가능하기는 하다)

seter 의존 관계 주입
 ・의존 관계 객체가 【선택적/변경 가능】일 때 주로 사용
 → 클래스 안에 선언된 의존관계 중 일부가 특정 상황에서 애플리케이션 실행 중 의존 관계 객체를 변경하고 싶은 경우(이런 일은 사실 거의 없으며, 있다고 하더라도
 다른 좋은 방법들이 많다)나 주입되는 객체가 스프링 컨테이너에 등록이 돼 있지 않고, 의존 관계 주입이 필수가 아니거나 외부 라이브러리 등의 객체를 주입
 해야 할 때 사용(이떄 setter 메서드 위에 @Autowired(required = false)를 사용) 　
 ※애플리케이션 실행 중 의존 관계 객체를 변경 : A 데이터 베이스 객체를 애플리케이션 실행 도중 B 데이터 베이스 객체로 변경하는 경우 등

좋은 방법의 예시(DB를 바꾸는 경우) 
여기서 중요한 철학 한 가지를 짚고 넘어 가자
→ "실행 중 의존관계 객체를 바꾸고 싶을 때는 의존 관계 객체를 바꾸지 말고 “행동(=객체가 할 수 있는 일 : 메서드)을 선택하라.”

1. 전략 패턴 (가장 많이 쓰는 방법)

핵심 아이디어
・서비스는 인터페이스만 의존
・실제 구현체는 전략으로 선택

인터페이스
public interface DataRepository {
    void save(String data);
}

구현체
@Component
public class MySqlRepository implements DataRepository {
    public void save(String data) {
        System.out.println("MySQL 저장");
    }
}
@Component
public class MongoRepository implements DataRepository {
    public void save(String data) {
        System.out.println("MongoDB 저장");
    }
}

전략 선택 서비스
@Service
public class DataService {

    private final Map<String, DataRepository> repositories;

    public DataService(Map<String, DataRepository> repositories) {
        this.repositories = repositories;
    }

    public void save(String type, String data) { 
        DataRepository repository = repositories.get(type);　// 행동 :  여기서 DB를 변경
        repository.save(data);
    }
}
dataService.save("mongoRepository", "data"); // 여기서 DB를 변경
👉 서비스 클래스에서 DB 의존 관계 객체 자체를 변경하지 않음.

2. Factory 패턴(이것도 실무에서 많이 사용)
@Component
public class RepositoryFactory {

    private final MySqlRepository mysql;
    private final MongoRepository mongo;

    public RepositoryFactory(
        MySqlRepository mysql,
        MongoRepository mongo
    ) {
        this.mysql = mysql;
        this.mongo = mongo;
    }

    public DataRepository getRepository(String type) {

        if(type.equals("mysql"))
            return mysql;

        if(type.equals("mongo"))
            return mongo;

        throw new IllegalArgumentException();
    }
}
서비스 클래스에서 DataRepository repo = factory.getRepository(type); 이렇게 가져옵니다.

3. Feature Flag / 설정 기반 전략 변경(요즘 많이 쓰는 방식)
핵심은 “이미 배포되어 있는 여러 로직 중에서 어떤 것을 사용할지 외부 설정 서버에서 선택"한다는 것이다. 
→ 이로 인해 요청에 대해 어떤 로직을 동적으로 적용할 지를 애플리케이션 코드에 추가 및 재빌드/재배포 없이 외부 설정 서버에게 맡길 수 있는 장점이 생긴다. 

1️.문제 상황부터 생각해봅시다
예를 들어 서비스에 두 가지 알고리즘이 있다고 합시다.
・A 알고리즘 (기존)
・B 알고리즘 (새로 만든 알고리즘)
새 알고리즘을 만들었는데 문제가 있습니다.
→바로 전체 사용자에게 적용하기는 위험

그래서 보통 이렇게 하고 싶습니다.
1. 일부 사용자만 새 알고리즘 사용
2. 문제 없으면 전체 적용
3. 문제 있으면 바로 다시 이전 알고리즘

문제는 코드를 이렇게 작성하면입니다.
→return newAlgorithm.process(); // 이렇게 되면 전체 사용자에게 새로운 알고리즘을 적용시켜 버리게 된다. 

2️.그래서 Feature Flag를 사용합니다
Feature Flag의 아이디어는 간단합니다.
→어떤 기능을 사용할지 "설정 값"으로 결정한다

예를 들어 설정이 이런 식입니다.
・new-algorithm = true
또는
・new-algorithm = false
→이 설정은 코드가 아니라 외부 서버에 있습니다.
예를 들어
・Spring Cloud Config
・LaunchDarkly
・자체 설정 서버

3️.그래서 코드가 이렇게 됩니다
@Component
public class OldAlgorithm {
    public String process() {
        return "A algorithm";
    }
}
@Component
public class NewAlgorithm {
    public String process() {
        return "B algorithm";
    }
}

그리고 서비스 코드

@Service
public class RecommendationService {

    private final OldAlgorithm oldAlgorithm;
    private final NewAlgorithm newAlgorithm;
    private final FeatureFlag featureFlag;

    public RecommendationService(
        OldAlgorithm oldAlgorithm,
        NewAlgorithm newAlgorithm,
        FeatureFlag featureFlag
    ) {
        this.oldAlgorithm = oldAlgorithm;
        this.newAlgorithm = newAlgorithm;
        this.featureFlag = featureFlag;
    }

    public String recommend() {

        if(featureFlag.isEnabled("new-algorithm")) {
            return newAlgorithm.process();
        }

        return oldAlgorithm.process();
    }
}

여기서 featureFlag.isEnabled("new-algorithm") 이게 하는 일은
→설정 서버에 물어봄　"new-algorithm 켜져 있어?"입니다.

・설정 서버
new-algorithm = false

・서비스 실행
if(false) {
   newAlgorithm.process();
} else {
   oldAlgorithm.process();
}

・필드 인젝션에 의한 의존관계 자동 주입
기본적으로는 필드 인젝션 사용은 금지. 왜냐하면 필드 인잭션으로는 순수 자바코드만으로 Mock 테스트 코드를 만드는 것이 불가능하다. 
(setter를 만들면 의존 관계 부분에 Mock 객체를 주입할 수 있겠지만 setter는 반드시 필요에 의해서만 만들어져야 하기에 함부로 만들면 안된다)
즉, setter가 없는 한 오로지 스프링 컨테이너에 의해서만 의존 관계 주입이 가능하기에 기본적으로 사용이 금지이다. 

그런데 단 예외가 있다. 필드 인젝션 방식의 의존관계 주입을 사용하는 클래스가 AppConfig 클래스 같이 절대로 순수 자바 코드로 테스트 할 일이 전혀
없을 때에는 필드 인젝션 방식을 사용해도 괜찮다. 
※AppConfig 클래스는 스프링 컨테이너에 의해서만 동작하는 케이스가 100%이다.




※테스트 코드 작성 관점에서는 생성자 방식이 수정자 방식보다 훨씬 좋다. 
ex) 수정자 방식의 경우

@Test
void test() {	
  OrderServiceImp order = new OrderServiceImp();
  order.createOrder(....); // nullpointerException 발생
}
→ 위 테스트는 스프링 컨테이너를 이용하지 않은 순수 자바 테스트 코드이다. 
그래서 OrderServiceImp 클래스에 의존관계 자동주입이 적용되지 않았다. 그래서 order.createOrder 메서드 호출 시 NullPointerException이 발생!!!!
테스트 코드 중 순수 자바 코드가 굉장히 많다. 근데 만약 수정자 방식 채택 시 위와 같은 실수를 범하기 마련이다. 
그러나 만약 생성자 방식의 의존 관계 주입을 했다면 new OrderServiceImp()에서 매개변수로 개발자가 직접 의존관계 객체를 주입해줘야 하므로 만약 의존관계 객체 주입을
누락시켰을 때 컴파일 에러를 미리 터트려 주기에 실수를 미리 방지 가능. 또한 의존관계 객체를 바로 볼 수 잇다는 장점도 존재.  


또 다른 장점 : 생성자 방식은 필드에 final 키워드를 붙일 수가 있기에 【불변 상태 유지/생성자 메서드 내의 로직 오류 및 누락】을 사전에 예방 가능
ex) 

@Component
class OrderServiceImp {

private final MemberRepository memberRepository;
private final DiscountPolicy discountPolicy;

public OrderServiceImp(MemberRepository memberRepository, DiscountPolicy discountPolicy) {
// 만약 개발자가 여기에다가 타입에 맞지 않는 객체를 주입하거나 주입을 누락시키면 
// 컴파일러 에러가 발생시켜서 런타임 에러를 방지해준다. 

} 


}
